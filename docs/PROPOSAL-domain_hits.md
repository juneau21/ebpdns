# PROPOSAL：`domain_hits` 的容量策略

> **状态：未实现（保持现状）。** 本文是容量策略的分析与待裁决项，不是已落地设计。
> **仅提案，本版不实现。**

## 1. 背景

`/api/status.rule_hits` 与 `/metrics` 的 `ebpdns_rule_hits_total` 需要按规则/域名聚合命中。
当前实现是**有界**的：命中表有固定容量上限，满时按既有策略淘汰，不会随查询域名数无限增长。
因此"内存会不会被打爆"的答案是"不会"，但"最热域名会不会被误淘汰"取决于容量与淘汰策略。

## 2. 原提案的选项

| 选项 | 做法 | 代价 |
|---|---|---|
| A. 固定条数 + LRU | 容量固定（如 4096），满即淘汰最久未用 | 突发热点可能挤掉长尾；实现最简单 |
| B. 固定条数 + TinyLFU | 用频率草图保护高频项 | 需要额外 sketch 内存；对扫描型流量更稳 |
| C. 分片 + 每片上限 | 按域名哈希分片，降低锁竞争 | 总量仍是各片之和，热点倾斜时利用率低 |
| D. 动态扩容 | 按 QPS 调整容量 | 内存不可预测，违反"容量有界"约定 |

## 3. 现状复核（与代码一致）

- 当前是**有界聚合**（不是无界 HashMap）；上限与淘汰策略在实现内固定，未暴露配置键。
- `rule_hits` 在 `/api/status` 中是可空对象；键不存在/为空表示"本窗口没有命中"，
  与"功能缺失"不同（0 值 KPI 口径见 `CONVENTIONS §11`）。
- `/metrics` 的 `ebpdns_rule_hits_total` 与 `/api/status.rule_hits` 同源，不得各算一套。

## 4. 待裁决

1. 是否需要把容量暴露为配置键（会新增可写键与门禁登记，属于接口扩展）；
2. 是否用 TinyLFU 替换现有淘汰策略（需要基准证明 hit 率提升且无内存回归）；
3. 是否需要"每规则"与"每域名"两张表（当前是一维聚合，扩表会改变 `/api/status` 形状）。

在上述裁决完成前，**保持现状**：有界、固定策略、不新增配置键、不改 API 形状。

## 5. 结论

本文只记录"当前已有界"的复核结论与代价数据，供后续裁决；**未实现，保持现状**。
**仅提案，本版不实现。**
