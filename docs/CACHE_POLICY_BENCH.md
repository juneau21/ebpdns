# 三种缓存策略命中率实测对比（ebpdns 2.1.49-p1，历史记录）

> **2.1.50 更新**：`tinylfu` 与 `partitioned` 策略**均已移除**（旧值启动/热重载时回退
> `s3fifo` 并 WARN；`cache_partitions` 键一并删除）。下文两张表是 **2.1.49-p1 的历史实测**，
> 只作对照记录；当前可选策略只有 `s3fifo` / `lru`。
>
> 目的（当时）：回答"lru / tinylfu / partitioned 哪种命中率高"。
> 方法：**假上游**隔离网络（本地 UDP，应答 < 0.2 ms），只让缓存策略成为变量。
> 环境：192.168.0.236，8 核 / 3.9 GB，ebpdns 2.1.49-p1（本包二进制）。

## 1. 负载模型

| 参数 | 值 |
|---|---|
| 查询速率 | 800 qps（实测 800 qps，p50 0.2 ms / p95 0.5 ms） |
| 名字池 | 5 000 个唯一名字（`n*.bench.test`） |
| 分布 | Zipf，α = 1.0（热点明显，接近真实上网行为） |
| 预热 | 30 s（大容量档 20 s） |
| 测量 | 60 s，冷启动，每次策略独立实例 |
| 判定 | `/api/status.counters` 的 hit / miss 增量 |

## 2. 结果 A：容量不足（`cache_size = 1024`，工作集 5000）

| 策略 | hit | miss | **命中率** | 实际占用 |
|---|---|---|---|---|
| **tinylfu** | 37 799 | 10 201 | **78.75 %** | 1024 |
| lru | 36 153 | 11 847 | 75.32 % | 1024 |
| partitioned | 32 442 | 15 558 | 67.59 % | **602** |

## 3. 结果 B：容量充足（`cache_size = 131072`，工作集 5000）

| 策略 | hit | miss | **命中率** | 实际占用 |
|---|---|---|---|---|
| lru | 46 568 | 1 432 | 97.02 % | 4302 |
| tinylfu | 46 568 | 1 432 | 97.02 % | 4302 |
| partitioned | 46 568 | 1 432 | 97.02 % | 4302 |

> 三种策略**逐位相同**：没有淘汰压力时，命中率只由"工作集 / TTL"决定，与策略无关。

## 4. 结论与建议

1. **容量不足时：历史数据里 TinyLFU 命中率最高**（比 LRU 高 3.4 个百分点，比 partitioned
   高 11.2 个百分点）。这是当时 W-TinyLFU 实现的实测结论；**该策略已于 2.1.50 移除**，
   当前默认 `s3fifo` 的小容量/抗扫描行为请以现行基准为准。
2. **容量充足时三者完全一致**（97.02 %）。此时换策略没有任何收益，不要折腾。
   判断标准看 `cache.used / cache.capacity`：
   - < 20 %：容量充足，**保持默认（s3fifo）即可**；
   - 接近 100 % 且命中率下滑：才是策略生效的场景（可选 `s3fifo` / `lru`）。
3. **partitioned 只在"多分组分流"时才有意义**。实测单分组流量下它按
   `domestic 0.2 / global 0.2 / default 0.6` 的权重切分容量，
   结果 1024 容量只用了 602（其余配额空转），命中率最低。
   → 除非确实配置了多组上游并需要按组隔离缓存，**不要选 partitioned**。
4. **生产现状**：235/236 当前为 `lru`，`used` 约 1 500 / 131 072（1.2 %），
   属于"容量充足"区 —— **命中率与策略无关**，现有 90 % 的命中率主要由 TTL（300 s）决定。
   因此在修完本包的缺陷后，**不必改策略**；若将来工作集接近容量，再切 `s3fifo`
   （`tinylfu` 已于 2.1.50 移除，不再可选）。

## 5. 如何复现

源码包 `tools/bench/` 下提供三个脚本：

```bash
# 1) 启动假上游
python3 tools/bench/fake_upstream.py 15453 &

# 2) [历史归因] 跑当时的两种策略（s3fifo / lru；2.2.0 起只剩 s3fifo，lru 已移除）
#    默认 size=1024 / pool=5000 / 800qps；当前代码只能复现 s3fifo 一侧
sudo SIZE=1024 POOL=5000 RATE=800 bash tools/bench/bench_driver.sh

# 大容量档
sudo SIZE=131072 POOL=5000 RATE=800 OUT=/root/bench-large.txt bash tools/bench/bench_driver.sh
```

脚本会为每种策略生成独立配置（`/tmp/bench-<policy>.json`）、独立端口
（DNS 127.0.0.1:15353、API 127.0.0.1:18360），**不会影响生产实例**。

## 6. 备注

- 本对比只测"命中率"，未测每查询 CPU 开销。实测三者 p50 都在 0.2-0.3 ms，
  8 核机器 800 qps 无压力；历史 TinyLFU 的 `sketch` 为 4 KB 定长，内存开销可忽略。
- 当前切换策略的方式：`PUT /api/config {"cache_policy":"s3fifo"}`（或 `"lru"`）+
  `POST /api/reload`（会增量迁移缓存，建议低峰执行）。`tinylfu` 已移除：写旧值会被
  `PUT /api/config` 拒绝（400），旧配置文件则在启动/热重载时 WARN 回退 `s3fifo`。
